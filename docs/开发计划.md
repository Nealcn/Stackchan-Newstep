## 1. 计划概述

### 1.1 计划目标

依据 PRD V1.1 目标 G1~G5：

- 基线能力（表情对话、人脸跟随、触控姿态互动、云端 AI 语音）全部验证并保持回归；
- 新增红外家电遥控（FR-05）：RMT 驱动 + NEC 编解码 + 码库 + 遥控屏；
- 硬件资源规则 RS-1~RS-4 落地（FR-06）；
- 打通 LLM→MCP 联动链路（FR-07）：≥3 条自然语言指令端到端成功；
- 交付固化固件 + 操作手册（D-1~D-5），总体验收 AC-1~AC-8 通过。

### 1.2 计划假设与前提

| 编号 | 假设 | 说明 |
|---|---|---|
| AS-1 | 开发人力 1 人（开发兼测试） | 若 2 人并行，P2/P3 可压缩约 25% |
| AS-2 | 全职投入按 5 工作日/周估算 | 工时均为工作日，允许 ±20% 偏差（AS-6） |
| AS-3 | **已完成前置工作**：源码获取、完整性验证、A 档清理（12MB→7.3MB）、git 基线建立（bb40170/7588955 两提交） | 见 [基线盘点与清理分析.md](基线盘点与清理分析.md) 第 5 节 |
| AS-4 | **本机不安装 ESP-IDF**（已确认无法安装）：代码在本机编写，编译/烧录/验证在具备 ESP-IDF ≥5.5 的验证机完成（见 1.4 异地验证工作流） | P1.1 调整为验证机环境准备与脚本适配 |
| AS-5 | 测试环境：2.4G WiFi、充电宝、待学习家电（空调/电视）及原装遥控器 | 缺省设备须在 P2.6 前备齐 |
| AS-6 | 单任务超期 ≥2 个工作日触发计划变更评审（第 9 节） | — |
| AS-7 | 基线当前为本地 git 仓库，每阶段结束提交一次里程碑 | 回滚与变更追溯的基础 |

### 1.3 关键成功因素

1. **P1 首次编译优先**：构建链路是本项目一切的前提，P1 不完成不进入任何开发；
2. **红外驱动范围收敛**：首期只做 NEC 协议（R-1），实测覆盖不足的协议记录待扩展，不无限投入；
3. **改动面控制**：基线文件只动 `m5stack_core_s3.cc` + `CMakeLists.txt`（架构 DP-6），每轮开发后 `git diff` 核对；
4. **回归不积压**：P2 起每轮固件更新即跑冒烟用例（第 8.3 节），不攒到 P4 集中测。

### 1.4 异地验证工作流（V1.1 新增：本机不开发现场编译）

**背景**：本机无法安装 ESP-IDF 5.5，编译/烧录/实测全部在验证机（具备 ESP-IDF ≥5.5 + K151 硬件）进行。

**工作流**

```
本机（开发）         git 提交/推送   验证机（编译验证）
写代码 ──────────────► 拉取 ──► 编译 → 烧录 → 冒烟测试 ──► 反馈问题清单 ──► 本机修复
```

**控制措施**

| 编号 | 措施 | 说明 |
|---|---|---|
| WV-1 | 验证机先编译基线成功（P1.2），再合入新增代码 | 区分「基线问题」与「新增代码问题」 |
| WV-2 | 新增代码按模块独立提交（ir_driver → codec → store → service → 集成） | 问题可用 `git log`/`git show` 定位到模块，支持 `git checkout` 单模块回退 |
| WV-3 | 本机代码质量靠「API 版本核对 + 人工审查」替代编译 | 写码前先核对 ESP-IDF 目标版本 API（docs.espressif.com），函数签名/结构体字段以文档为准 |
| WV-4 | 高风险 API（RMT/中断）先用最小验证用例在验证机先行 | 驱动层单独编译验证后再做上层 |
| WV-5 | 预留 2~3 个「编译往返」调试轮次到 P2 工期 | 无本地编译的纠错成本计入计划（P2.1~P2.2 已含） |

**验证机就绪清单**（P1 前确认）：ESP-IDF ≥5.5 环境、Python、USB 串口驱动、K151 整机 + 充电线、2.4G WiFi。

## 9. 计划变更管理

触发条件（任一）：

1. 单任务延期 ≥2 个工作日（超出缓冲消化能力）；
2. 外部依赖中断 ≥1 周（ESP-IDF 下载、云服务、家电设备）；
3. 红外协议覆盖范围调整、功能增减、硬件/服务约束变化；

处理流程：开发提出变更说明（影响范围、工期影响、方案）→ 评审确认 → 更新本计划（0.1 追加条目）→ 按新计划执行。旧版本基线由 git 提交历史保留。
