## 1. 关键结论摘要（TL;DR）

1. **基线不是官方 stack-chan 固件，而是 xiaozhi-esp32 v2.2.6（小智 AI 聊天机器人）的深度定制分支**——由 Nealcn 把 StackChan K151 的舵机云台、三区触摸、IMU、表情屏等硬件全部适配进了小智生态。`sdkconfig.defaults` 第 1 行 `CONFIG_BOARD_TYPE_M5STACK_CORE_S3=y`（K151 以 CoreS3 为基板）。
2. **PRD 5 项核心功能中，2 项基线已完整实现、1 项部分实现、2 项完全缺失**：触控+姿态互动 ✅（超额实现）、云端 AI 语音 ✅（核心且成熟）、云台摄像头 ⚠️（人脸跟随+拍照问答形态，无手机推流）、Avatar 真人动作复刻 ❌（无此功能）、红外家电遥控 ❌（无任何红外代码）。
3. **基线没有「首页滑动多页面」机制**——UI 是单屏 LVGL 聊天界面（顶栏/聊天区/表情区/底栏），PRD 的「4 页面滑动切换」交付形态需要新建。
4. **基线独有的架构优势**：MCP 设备控制体系（15 个工具）是现成的「语音指令 → 设备控制」通道，红外遥控可做成 `self.ir.*` MCP 工具接入，联动链路比 PRD 设想的更简单。
5. **清理结论**：约 8.7MB 内容明确可删（98 个无关板目录、36 个未启用语言包、docs/v0、备份与重复文件等），仓库可从 12MB 缩至约 3~4MB；但**建议先完成一次成功构建再清理**。

## 2. 基线概况

### 2.1 身份与版本

| 项 | 值 |
|---|---|
| 项目名 | xiaozhi（PROJECT_VER "2.2.6"，顶层 CMakeLists.txt） |
| 生态 | 小智 AI（ESP-SR 唤醒词 + 小智云流式 ASR/LLM/TTS + MCP 设备控制） |
| 芯片 | ESP32-S3（240MHz，16MB QIO Flash，四线 80M PSRAM） |
| 框架 | ESP-IDF ≥ 5.5.2，Google C++ 代码风格 |
| 目标板 | M5Stack CoreS3（K151 基板），另适配约 100 块板（本机只用 CoreS3） |
| 唤醒词 | 自定义「土豆土豆」（`tu dou tu dou`，Multinet6 命令词模型） |
| 云服务 | 默认 xiaozhi.me / 自建服务器（OTA 可配置，默认官方 api.tenclass.net） |
| 语言 | 中文为主（assets 支持 38 语言，仅 zh-CN/en-US 参与构建） |

### 2.2 仓库结构（构建相关）

```
code/
├── CMakeLists.txt            # 项目入口（PROJECT_VER 2.2.6, MINIMAL_BUILD ON）
├── main/                     # 全部应用源码（约 9.5MB）
│   ├── application.cc        # 主应用：事件循环、对话状态机、网络事件
│   ├── device_state_machine* # 设备状态机（11 状态 + 白名单迁移）
│   ├── mcp_server.cc         # MCP 服务器（15 个工具）
│   ├── audio/                # 音频管线：codecs/processors/wake_words
│   ├── display/              # LVGL 显示层 + 聊天 UI
│   ├── protocols/            # MQTT(TLS) / WebSocket 协议
│   ├── boards/               # 100 个板目录（仅 m5stack-core-s3 + common 参与编译）
│   │   └── m5stack-core-s3/  # ★ StackChan 定制：舵机/人脸追踪/触摸/IMU/表情/LED
│   └── idf_component.yml     # 23+ 个 ESP-IDF 注册表组件（构建时联网下载）
├── partitions/v1/16m_stackchan.csv   # ★ 唯一生效分区表（model 4MB+双 app 3MB+assets 6MB）
├── sdkconfig.defaults        # ★ 本机配置（板型/唤醒词/摄像头/分区表/OTA）
├── sdkconfig.defaults.esp32s3        # S3 芯片配置（16MB/PSRAM/缓存）
├── scripts/                  # release.py（板 README 指定的编译入口）等 14 项
├── docs/                     # 上游多语言文档 + v0/v1 图片
└── BUGFIX.md / README*.md    # Nealcn 的 StackChan 修复记录与自定义说明
```

**板选择机制**：`main/CMakeLists.txt` 按 `CONFIG_BOARD_TYPE_*` 单分支选择，`file(GLOB)` 只编译 `m5stack-core-s3/*.cc`——**其余 98 个板目录完全不参与编译**（这是清理的最大依据）。

### 2.3 构建与烧录

- 官方入口：`python ./scripts/release.py m5stack-core-s3`（板级 README 指定）
- 手动：`idf.py build` / `idf.py -p COM6 flash`；进下载模式需长按复位键 3 秒至绿灯
- ⚠️ 仓库内 `build.bat` / `flash.bat` / `build_clean2.bat` 写死作者本机路径（`D:\Stackchan`、`D:\esp-idf`、`D:\Espressif`、工具链精确版本、COM6）——**本机不能直接运行，需适配**
- ⚠️ 首次构建需联网下载 23+ 个组件（components.espressif.com 注册表），断网会失败
- ⚠️ 当前是 zip 解压目录（无 `.git`）——任何修改前建议先 `git init` 建立版本基线

## 4. 与 PRD 五项核心功能对照

### 4.1 对照表

| PRD 功能 | 基线现状 | 差距 | 建议 |
|---|---|---|---|
| 1. Avatar 真人动作复刻 | ❌ **无**。有程序化表情 Avatar + 摄像头**人脸跟随**（云台跟着你动，不是复刻你的动作） | 大：官方 stack-chan 的复刻功能不在本生态 | 降级为「表情对话 + 人脸跟随」交付；动作复刻需从零开发姿态估计，难度高且无现成方案，不建议 |
| 2. 云台监控摄像头模式 | ⚠️ **部分**。摄像头+舵机已联动（FaceTracker）；MCP 有**拍照问答**（LLM 看图）；**无**手机推流监控 | 中：无 StackChan World APP 推流生态（本固件对接小智云端） | 改造为「拍照问答/人脸跟随」形态；如需推流需自研（H.264 推流工作量大，建议砍掉） |
| 3. 触控+姿态趣味互动（常驻） | ✅ **完整实现且超预期**。SI12T 三区摸头 + FT6336 手势 + BMI270 摇晃/抱起，全部常驻任意状态生效，联动语料/表情/舵机/LED | 无 | **直接复用，PRD 此项验收即通过** |
| 4. 联网云端 AI 语音助手 | ✅ **核心功能，成熟**。流式 ASR/LLM/TTS、语音打断、自定义唤醒词 | 无 | **直接复用**。注意：对接的是小智云端（xiaozhi.me 或自建），不是 StackChan World |
| 5. 红外家电遥控 | ❌ **无**。无红外驱动、无 IR 组件、无社区 MOD 生态（MOD 是官方 stack-chan 的概念，本生态是 ESP-IDF 组件） | 大：需从零新增 | 新增 ESP-IDF 红外模块（RMT 收发 + 学习/发射），做成 MCP 工具 `self.ir.*` 接入——这是本基线独有的低成本路径 |

### 4.2 关键差异与影响（必须向 PRD 反馈）

| # | 差异 | 影响 |
|---|---|---|
| D1 | 基线是**单屏聊天 UI**，无「首页滑动 4 页面」机制 | PRD 交付形态（C-3）需重新定义：多模式共存于同一聊天界面，由语音/触摸/MCP 触发，而非页面切换 |
| D2 | 无 StackChan World APP 生态 | 依赖该 APP 的功能（动作复刻、远程监控）不成立；设备绑定走小智云端 |
| D3 | 舵机/摄像头/IMU 在**板级自动运行**（人脸跟随常驻），无「模式」概念 | PRD 的「摄像头独占互斥（Avatar vs 监控）」不适用——本基线摄像头用途是跟随+拍照，不存在双视频冲突 |
| D4 | MCP 是现成的**语音→设备控制**通道 | 红外联动的实现路径比 PRD 设想更优：LLM 语义理解 → 直接调 `self.ir.*` 工具，无需自制「口令表+联动引擎」 |
| D5 | 唤醒词/昵称是「土豆土豆/土豆」 | 文案、语料池均围绕「土豆」人格，交付文案需沿用或整体更换 |

### 4.3 对既有文档的修正建议

1. **开发需求文档**：重写 FR-01（Avatar→表情对话+人脸跟随）、FR-02（监控→拍照问答）、FR-05（红外→MCP 工具方案）；删改 C-3（滑动页面）为「单界面多能力共存」；RS 规则表大部分失效（无多模式互斥问题），保留发码暂停摄像头等硬件级规则。
2. **架构设计文档**：TC-1 已有答案——基线为 **ESP-IDF C++**，融合层接口伪代码需改 C++ 形态；「资源仲裁器」退化为「硬件资源管理器」（摄像头/舵机/红外 的启停调度）；LinkageEngine 由 MCP 工具注册替代。
3. **开发计划**：P1（原生功能验证）验收项替换为基线实有功能（唤醒词/对话/互动/拍照问答）；P2 的红外「MOD 选型」改为「红外驱动自研 + MCP 工具注册」；P3 的「首页 4 页面」改为「红外功能集成进对话 UI」。

### 5.3 C 档：必须保留

- `main/boards/m5stack-core-s3/`（全部，含 SCS*.cc 舵机库、cores3_audio_codec、config.h）
- `main/boards/common/`、`main/` 全部源码（application/audio/display/protocols/led/mcp_server 等）
- `sdkconfig.defaults`、`sdkconfig.defaults.esp32s3`、`partitions/v1/16m_stackchan.csv`
- `scripts/release.py`、`build_default_assets.py`、`gen_lang.py`（构建链路直接调用）
- `main/assets/locales/zh-CN`、`en-US`、`main/assets/common/`
- 顶层 `CMakeLists.txt`、`README.md`、`BUGFIX.md`、`LICENSE`、`.gitignore`、`.clang-format`
- `build.bat` / `flash.bat`（**保留但需适配路径**，见 5.4）

### 5.4 构建脚本适配（交付前必做）

`build.bat`/`flash.bat` 写死了作者本机环境（`D:\Stackchan`、`D:\esp-idf`、`D:\Espressif`、精确工具链版本、COM6），三选一处理：

1. 把路径抽为变量并改成本机 ESP-IDF 安装位置（推荐，保留脚本便捷性）；
2. 删除 bat，改用标准流程：`idf.py build` / `idf.py -p <串口> flash`（ESP-IDF 官方环境）；
3. 统一以 `python ./scripts/release.py m5stack-core-s3` 为编译入口（板 README 官方方式）。

### 5.5 清理执行建议（顺序很重要）

1. **先 `git init` + 首次提交**（当前是 zip 解压、无版本控制——任何修改前必须建立基线，否则无法回滚）；
2. **先完成一次成功构建**（`idf.py build` 或 release.py）——确认基线可编译后再清理，避免「清理误删了构建依赖」与「原本就不能编译」两类问题混淆；
3. 删除 A 档（零风险，立即见效）；
4. B 档视需求归档到仓库外目录或 git 分支（保持与上游差分能力）；
5. 清理后重新构建 + 全量冒烟验证；
6. 最后适配 build.bat/flash.bat 路径。
